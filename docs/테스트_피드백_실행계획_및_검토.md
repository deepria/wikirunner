# 테스트 피드백 실행 계획 및 검토

- 작성일: 2026-07-29
- 범위: 테스트 피드백의 **수정 계획**, 구현 진행도와 신규 제안의 **실현 가능성 검토**.

## 결론과 우선순위

공정 플레이에 직접 영향을 주는 항목을 먼저 처리한다. 특히 우측 사이드바와 `분류:` 링크는 현재 차단 의도는 있으나 실제 나무위키 DOM에서 회귀가 있었으므로, 선택자 보강만 하지 않고 실제 Chrome 검증을 완료 조건으로 둔다.

| 우선순위 | 묶음 | 완료 기준 |
| --- | --- | --- |
| P0 | 공정 플레이 보완 | 경기 탭에서 금지 UI·분류 링크가 숨겨지고, 금지 링크 호버/클릭과 새 탭이 일관된 경고로 남는다. |
| P0 | 방 화면 재구성 | 시작·목표와 현재 경기 상태가 첫 화면에서 가장 먼저 읽히며, 방 코드는 보조 정보로 축소된다. |
| P1 | 방 나가기·강퇴 | 대기실 인원 관리가 서버 권한과 상태 전이에 맞게 동작하고, 경기 기록을 훼손하지 않는다. |
| P1 | 랭킹 기준 | 방장이 횟수순/시간순을 정하고 해당 기준이 게임 시작 시 고정되어 결과와 실시간 현황에 반영된다. |
| P2 | 점수·레이팅·매칭·아이템 | 공정성 데이터와 운영 정책을 선행한 뒤 별도 기능 단위로 설계한다. |

## 수정 계획

### 1. 우측 사이드바 숨김 재수정

이 항목은 경기 탭에만 적용한다. 평상시 나무위키 탐색 화면과 광고·일반 우측 콘텐츠는 바꾸지 않는다.

1. 최신 나무위키 화면에서 `실시간 검색어`, `최근 변경` 카드의 실제 DOM·반응형 구조를 다시 채집한다. 텍스트를 포함하는 모든 `div`를 넓게 탐색하는 방식은 중단한다.
2. 카드 제목을 기준으로 가장 가까운 카드 컨테이너만 찾는 전용 탐색 함수를 만든다. 카드가 비동기로 다시 그려질 때만 지연 적용되는 `MutationObserver`를 사용한다.
3. 감춰진 대상은 `display: none`으로 처리하고, 숨김 대상·미대상(광고, 문서 본문, 확장 오버레이)을 DOM fixture 테스트로 구분한다.
4. 다크/라이트 모드와 데스크톱·좁은 폭에서 실제 Chrome 수동 검증을 한다. 각 화면에서 경기 시작 전에는 표시되고, 경기 시작 뒤에는 두 카드만 사라지며, 경기 종료 뒤 다시 나타나야 완료다.

### 2. 문서 상단의 `분류:` 링크 제한

1. URL 정규화 규칙과 별도로, 경기 중에는 문서 상단 분류 바·분류 트리에서 출발한 링크를 금지 대상으로 판정한다.
2. `/w/분류:*` 문서 자체, 분류 바 안의 링크, 파일·특수 이름공간과 편집·토론·역사 링크는 모두 금지한다.
3. 일반 본문 안의 일반 문서 링크만 이동으로 인정한다. 외부 링크·앵커·검색·랜덤·헤더/사이드바 내 문서 링크는 인정하지 않는다.
4. 클릭은 막고 위반 사유를 `blocked_category_link` 또는 일반화된 `blocked_navigation`으로 기록한다. 기존 경고 화면에는 사람이 읽을 수 있는 사유를 표시한다.

### 3. 금지 링크 호버 경고와 규칙

**게임 규칙(초안)**

| 구분 | 허용 여부 | 처리 |
| --- | --- | --- |
| 본문 영역의 일반 문서 링크 | 허용 | 정상 이동 기록 |
| 문서 상단 `분류:` 및 분류 문서 | 금지 | 클릭 차단·경고 |
| 검색, 랜덤 문서, 실시간 검색어, 최근 변경 | 금지 | UI 숨김, 남은 링크 클릭 차단·경고 |
| 헤더·메뉴·사이드바의 문서 링크 | 금지 | 클릭 차단·경고 |
| 편집·토론·역사, 파일, 외부 URL, 페이지 내 앵커 | 금지 | 클릭 차단·경고 |
| 뒤로/앞으로/새로고침 | 허용하되 이동 횟수 제외 | 기존 기록 정책 유지 |

1. Content Script에 링크 판정 함수 하나를 두고, URL·DOM 위치·링크 성격을 함께 판정한다. 서로 다른 이벤트 핸들러가 각자 규칙을 갖지 않게 한다.
2. 금지 링크에 마우스를 올리면 확장 오버레이 근처에 짧은 사유(예: `분류 링크는 경기 중 사용할 수 없습니다`)를 표시하고 금지 커서를 적용한다. 터치 환경에서는 첫 탭에 사유, 다음 탭에도 차단을 유지한다.
3. 클릭·키보드 활성화·중간 클릭을 모두 차단하고, 같은 유형의 경고가 과도하게 쌓이지 않도록 짧은 중복 억제 시간을 둔다.
4. 허용/금지 표본 URL과 DOM 위치를 자동 테스트로 만들고, 실제 나무위키의 DOM 변경 시 같은 시나리오를 재실행한다.

### 4. 브라우저 검색 기능 제한

페이지 검색창, `/`, `Ctrl/⌘+K` 등 페이지에 전달되는 입력은 기존처럼 차단·경고할 수 있다. 그러나 Chrome 자체의 `Ctrl/⌘+F` 찾기 창은 브라우저 단축키여서 Content Script가 항상 가로채거나 비활성화할 수 있다고 보장할 수 없다. 확장 프로그램 명령도 운영체제·Chrome 단축키보다 우선할 수 없다. [Chrome Commands 문서](https://developer.chrome.com/docs/extensions/reference/api/commands?hl=en)

따라서 이 항목은 다음처럼 처리한다.

1. `Ctrl/⌘+F`를 Windows·macOS Chrome에서 실제로 재검증하고, 페이지로 전달되는 경우에만 차단/경고를 추가한다.
2. 전달되지 않는 경우는 기술적으로 강제 차단 대상으로 약속하지 않는다. 경기 규칙과 경고 정책에 `브라우저 찾기 사용 금지`를 명시하고, 별도 위반 자동 판정은 하지 않는다.
3. 경쟁성 높은 모드가 필요해지면 브라우저 확장만으로 해결하려 하지 않고, 전용 클라이언트·감독 모드 등 별도 신뢰 모델을 검토한다.

### 5. 방 내부 UI/UX 개선

1. 상단을 `현재 경기` 중심으로 재구성한다. 시작 문서 → 목표 문서를 큰 대비와 방향 표기로 한 줄에 배치하고, 상태·카운트다운·시작 버튼을 바로 아래에 둔다.
2. 방 코드는 헤더의 작은 복사 가능한 칩으로 축소한다. 안내 문구는 처음 입장했을 때만 보이게 하거나 보조 영역으로 내린다.
3. 참가자 영역에는 연결·준비·방장 상태를 일관된 배지로 표시하고, 방장용 강퇴는 P1 정책이 적용된 경우에만 노출한다.
4. 실시간 경기 현황은 순위, 닉네임, 선택된 핵심 기준(횟수 또는 시간), 보조 기준, 상태 순으로 표 형태를 재배열한다. 이동 경로는 행을 펼칠 때만 불러오는 현재 방식을 유지한다.
5. 모바일/좁은 화면에서는 시작·목표를 세로로 전환하고, 실시간 현황은 핵심 열을 우선해 가로 스크롤 없이 읽히게 한다.

**완료 기준:** 방 코드보다 시작·목표를 먼저 인지할 수 있고, 2~8명 상태에서 순위·준비 상태·다음 행동을 한 화면에서 이해할 수 있어야 한다. 구현 뒤 키보드 탐색, 모바일 폭, 다크 테마를 점검한다.

### 6. 방 나가기와 강퇴

**정책을 먼저 고정한다.** 현재 참가자와 경기 기록은 연결되어 있으므로, 행을 삭제하는 방식은 사용하지 않는다.

1. 대기 상태에서는 참가자가 `방 나가기`를 누르면 활성 참가자 목록에서 빠지고 정원이 즉시 반환되도록 한다.
2. 방장은 대기 상태에서 다른 참가자에게만 `강퇴`를 실행할 수 있게 한다. 본인은 나갈 수 없으며, 방을 종료하거나 방장 위임 정책이 확정되기 전까지는 방장 이전을 제공하지 않는다.
3. 카운트다운·경기 중에는 인원 삭제/강퇴를 막는다. 참가자의 자발적 포기는 기존 `abandon`으로 기록하고, 방장은 기존 `경기 종료`를 사용한다. 경기 중 임의 강퇴는 순위와 결과의 신뢰를 훼손하므로 P1 범위에서 제공하지 않는다.
4. 서버에 `leave`·`kick` 명령, 권한 검사, 낙관적 버전 검사와 감사 가능한 종료 사유를 추가한다. 스냅샷은 퇴장자를 현재 참가자 수에서 제외하되, 끝난 게임의 기록은 계속 조회할 수 있게 한다.
5. 웹에는 본인용 퇴장 버튼과 방장용 참가자 행의 강퇴 버튼·확인 대화상자를 추가한다.

**검증:** 일반 참가자 퇴장, 방장 외 강퇴 시도 거부, 방장의 강퇴, 정원 재입장, 카운트다운/경기 중 거부, 종료 후 결과 보존을 API·브라우저 다중 프로필에서 확인한다.

### 7. 랭킹 기준: 횟수순/시간순

1. 방 설정에 `랭킹 기준`을 추가한다. 값은 `횟수순` 또는 `시간순`이며 방장만 대기 상태에서 변경할 수 있다.
2. 게임을 시작할 때 기준을 게임 스냅샷에 고정한다. 경기 도중이나 결과 화면에서 기준을 바꾸지 않는다.
3. **횟수순:** 완주자 중 `이동 횟수` 오름차순, 동률이면 `완주 시간` 오름차순, 다시 동률이면 서버가 기록한 완주 시각 순으로 정렬한다.
4. **시간순:** 완주자 중 `완주 시간` 오름차순, 동률이면 `이동 횟수` 오름차순, 다시 동률이면 서버 완주 시각 순으로 정렬한다.
5. 미완주·포기·검토 중 상태는 순위 번호를 부여하지 않고, 리더보드 하단에 상태별로 표시한다. 리더보드의 열과 보조 문구도 선택한 기준에 맞춘다.

**시간순 점수화 검토 결과:** 기술적으로는 가능하다. 서버가 이미 서버 수신 시각으로 `durationMs`를 보유하므로, 예를 들어 시간 등급 또는 `기준 시간 / 실제 시간` 방식의 점수를 계산할 수 있다. 다만 문서 조합마다 난이도 편차가 매우 커서, 지금 점수를 누적 레이팅이나 보상에 쓰면 불공정해진다. P1에서는 **정렬만** 도입하고, 난이도 보정 데이터가 쌓인 후 P2에서 경기별 표시 점수를 실험한다.

## 검토 항목 결과

### 1. 플랫폼 내부 iframe으로 나무위키 표시

**불가(현 구조에서는 비권장).** 나무위키 응답은 `X-Frame-Options: SAMEORIGIN`을 보내므로 WikiRunner 도메인에서 iframe으로 표시할 수 없다. 우회 프록시는 저작권·보안·로그인/광고 정책과 문서 이동 검증을 모두 복잡하게 만든다. 현재처럼 전용 나무위키 경기 탭과 확장 오버레이를 유지한다.

### 2. 새 탭으로 열었을 때 경고 처리

**구현되어 있으며 정책 보정이 필요하다.** 현재 확장은 경기 중 별도 나무위키 탭 이동을 `new_tab` 경고로 기록한다. 다만 일반 탭 전환도 오탐이 될 수 있어 자동 실격 근거로 쓰지 않는다. P0의 링크 판정/호버 경고와 함께 `새 탭 열기는 금지, 경고는 검토용`으로 안내를 명확히 하고 다중 프로필 회귀 테스트를 추가한다.

### 3. 뎁스 기반 난이도

**동의: 단독 지표로는 의미가 작다.** 현재 랜덤 워크의 깊이는 생성 경로 길이일 뿐, 실제 최단 경로나 문서의 링크 밀도, 우회 가능성, 주제 친숙도를 반영하지 못한다. 당장은 쉬움/보통/어려움 문구를 `생성 경로 길이`로 정확히 표현하고, 이후 실제 완주 시간·이동 수·완주율·경고율을 수집해 난이도 등급을 보정한다.

### 4. 생성 경로를 LLM으로 더 나은 경로로 변경

**조건부 가능, 자동 확정은 불가.** LLM은 후보 경로를 더 흥미로운 주제 전환, 중복 감소, 목표 난이도에 맞게 **추천·재정렬**하는 데 사용할 수 있다. 하지만 존재하지 않는 문서나 실제 링크가 아닌 연결을 만들 수 있으므로, 최종 경로는 확장 프로그램이 각 문서와 인접 링크를 브라우저에서 재검증한 경우에만 저장한다. 서버가 나무위키 링크를 재요청해 독립 검증하지 못하는 현재 제약도 유지된다.

권장 순서는 `랜덤 후보 여러 개 생성 → LLM이 후보를 평가/선택 → 확장이 실제 링크 재검증 → 방장이 최종 확인 → 서버 스냅샷 고정`이다. 비용, 응답 지연, 전달할 문서 제목의 외부 전송 고지를 먼저 정한 뒤 실험 기능으로 시작한다.

### 5. 유저 레이팅 시스템

**가능하지만 P2.** 익명 계정만으로는 부계정 생성과 재가입을 막기 어렵고, 문서 난이도가 보정되지 않은 상태의 승패/시간은 안정적인 실력 신호가 아니다. 먼저 고정된 랭킹 규칙, 경기 무효/경고 처리, 난이도 데이터, 계정 정책을 마련한다. 이후 Glicko-2 또는 TrueSkill 계열의 별도 `rating_history`를 두고, 친선전과 레이팅전을 분리하는 설계를 권장한다.

### 6. 레이팅 간 랜덤 매칭

**가능하지만 레이팅 이후 단계.** 대기열, 허용 레이팅 차의 시간별 확장, 취소/재접속, 지역·언어, 경기 설정 자동 선택과 매칭 실패 UX가 필요하다. 방 코드 기반의 친구 초대와는 운영 모델이 다르므로, 레이팅 시스템과 활성 이용자 규모가 확인된 뒤 별도 모드로 도입한다.

### 7. 사용 가능 아이템

**가능하나 경쟁 모드와 분리 필요.** 예시의 `이번 문서에 목표가 있으면 자동 클리어`는 서버가 검증 가능한 조건과 1회성 소비 기록이 있어야 한다. 아이템 보유량, 사용 시점, 효과, 취소·재시도, 경기 결과 반영을 서버 트랜잭션으로 처리해야 한다. 친선/이벤트 모드부터 실험하고 레이팅전에는 기본 비활성화한다.

### 8. 확장 프로그램 ↔ 방 연동 자동화

**가능하며 권장(P2).** 현재의 1회용 페어링 코드 입력은 안전하지만 마찰이 있다. 웹의 `확장 프로그램 연결` 버튼에서 서버가 짧은 수명의 1회용 nonce를 만들고, WikiRunner 웹 도메인에 주입된 Content Script가 사용자 클릭 뒤 이를 확장 Service Worker로 전달해 소비하는 방식으로 자동화할 수 있다. 페이지와 확장의 직접 신뢰 대신 서버 nonce를 사용하고, 첫 연결은 명시적 사용자 확인을 유지한다. Content Script는 지정 URL과 프레임에서만 주입되므로 매니페스트의 대상 도메인·프레임 설정을 함께 검토한다. [Chrome Content Scripts 문서](https://developer.chrome.com/docs/extensions/reference/manifest/content-scripts?authuser=117)

## 권장 실행 순서

1. P0 공정 플레이: 실제 DOM 수집 → 사이드바/분류/링크 판정 단일화 → 호버 경고 → 실제 Chrome 회귀.
2. P0 방 UI: 시작·목표 우선 레이아웃과 실시간 현황을 먼저 개편한다.
3. P1 방 나가기·강퇴: 상태 전이와 API·DB를 추가한 뒤 UI를 연결한다.
4. P1 랭킹 기준: 설정 고정, 서버 정렬, 리더보드 표시 순으로 도입한다.
5. P2 후보 중 자동 연동을 먼저 작은 실험으로 검증하고, 난이도 데이터가 쌓인 뒤 점수·레이팅·매칭·아이템을 판단한다.

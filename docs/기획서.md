# WikiRunner 기획서

## 1. 프로젝트 개요

**WikiRunner**는 참가자가 나무위키 문서 사이의 내부 링크만 따라가며, 주어진 시작 문서에서 목표 문서까지 가장 빨리 도착하는 멀티플레이 스피드런 게임이다.

게임은 별도의 웹 서비스에서 방과 순위를 관리하고, 브라우저 확장 프로그램이 실제 나무위키 탐색을 안내하고 이동 기록을 수집하는 구조로 운영한다.

> MVP 원칙: 친선 플레이를 위한 신뢰 기반 게임으로 시작한다. 모든 부정행위를 완벽히 차단하기보다, 정상적인 링크 이동을 기록하고 명백한 위반을 표시하는 데 집중한다.

### 목표

- 친구들과 짧은 시간 안에 함께 시작하고 경쟁할 수 있다.
- 같은 출발점과 목표를 공유해 공정한 기록을 만든다.
- 어떤 문서를 거쳐 갔는지 경로를 리플레이처럼 확인할 수 있다.

### 비목표 (MVP)

- 현금·상품이 걸린 대회의 완전한 부정행위 방지
- 나무위키 전체 문서 그래프 수집 및 최단경로 계산
- 계정 기반 영구 랭킹, 친구 시스템, 관전 기능
- 모바일 브라우저 지원

## 2. 핵심 게임 규칙

| 항목 | 내용 |
| --- | --- |
| 시작 | 방장이 정한 시작 시각에 참가자 전원을 시작 문서로 이동시킨다. |
| 목표 | 화면 상단 오버레이에 목표 문서 제목을 표시한다. |
| 이동 | 현재 문서 본문에 있는 나무위키 내부 문서 링크를 클릭해서만 이동한다. |
| 완주 | 목표 문서의 canonical URL에 도달하면 자동으로 기록한다. |
| 승패 | 서버 기준 경과 시간이 짧은 순으로 순위를 정한다. 동점이면 이동 횟수가 적은 쪽이 앞선다. |
| 뒤로가기 | 허용한다. 방문 기록에는 남지만 이동 횟수에는 포함하지 않는다. |
| 새로고침 | 허용한다. 현재 문서와 게임 상태를 복원한다. |
| 검색·주소창·새 탭 | MVP에서는 위반으로 표시한다. 자동 실격 대신 방장이 판단할 수 있다. |

### 문서 범위

- 허용: `/w/` 형태의 일반 문서 링크
- 제외: 편집, 토론, 역사, 역링크, 파일, 분류, 외부 링크 및 앵커 이동
- 시작/목표 문서는 운영자가 준비한 **문서 풀**에서 고른다.
- 문서 풀에는 동음이의어, 삭제·이동 가능성이 높은 문서, 성인·민감 문서를 넣지 않는다.

## 3. 사용자와 사용 흐름

### 사용자 역할

- **방장**: 방 생성, 문서 선택, 시작 시각 설정, 게임 시작 및 결과 확정
- **참가자**: 초대 코드로 방 입장, 확장 프로그램 연결, 경기 진행

### 방장 흐름

1. 웹에서 방을 만들고 닉네임을 입력한다.
2. 시작·목표 문서를 직접 선택하거나 문서 풀에서 랜덤으로 뽑는다.
3. 방 코드 또는 초대 링크를 공유한다.
4. 모든 참가자가 준비되면 10초 카운트다운을 시작한다.
5. 실시간 순위와 위반 표시를 보고 결과를 확정한다.

### 참가자 흐름

1. Chrome 확장 프로그램을 설치한다.
2. 웹의 방 코드로 입장하고 닉네임을 정한다.
3. 확장 프로그램에서 같은 방 코드로 연결한 뒤 준비 상태가 된다.
4. 카운트다운 종료와 함께 시작 문서가 열린다.
5. 내부 링크를 따라 목표 문서에 도달한다.
6. 결과 화면에서 순위, 시간, 클릭 수, 이동 경로를 확인한다.

## 4. 화면 구성

### 웹 서비스

| 화면 | 주요 요소 |
| --- | --- |
| 홈 | 방 만들기, 방 코드 입력, 게임 소개, 확장 프로그램 설치 안내 |
| 방 대기실 | 방 코드, 시작/목표 문서, 참가자·준비 상태, 방장 설정, 시작 버튼 |
| 경기 현황 | 참가자별 상태, 완주 순서, 경과 시간, 위반 경고 |
| 결과 | 최종 리더보드, 각 참가자의 이동 횟수·경로·경고, 다시 하기 |

### 브라우저 확장 오버레이

나무위키 문서 오른쪽 상단에 작고 접을 수 있는 패널을 표시한다.

```text
WikiRunner
목표: 담비(서비스)
시간: 01:24.53
이동: 7회
상태: 진행 중
```

- 대기 중에는 방 연결 상태와 카운트다운을 표시한다.
- 경기 중에는 목표, 시간, 이동 횟수, 연결 상태를 표시한다.
- 완주 후에는 기록 전송 성공 여부와 최종 순위를 표시한다.

## 5. 기능 요구사항

### P0 — MVP 필수

- 6자리 방 코드 생성과 방 입장
- 익명 닉네임 기반 참가자 관리
- 방장 설정: 시작 문서, 목표 문서, 최대 인원, 시작
- 서버 기준 카운트다운 및 동시 경기 시작
- 확장 프로그램의 목표/타이머 오버레이
- 내부 링크 클릭 이벤트와 방문 경로 기록
- 목표 도달 자동 감지 및 완주 시간 산정
- 실시간 대기실·경기 현황·결과 리더보드
- 이탈 및 재연결 상태 표시

### P1 — MVP 다음

- 문서 풀 난이도 태그와 랜덤 매치
- 경로 리플레이 및 공유 링크
- 일일 챌린지
- 로그인, 전적, 개인 기록
- 관전자 모드와 방 공개 설정

## 6. 기록 및 검증 정책

각 정상 이동은 다음 정보를 가진다.

```json
{
  "sequence": 4,
  "fromArticle": "K리그",
  "toArticle": "축구",
  "clickedAt": "2026-07-27T06:00:12.340Z",
  "previousHash": "...",
  "eventHash": "..."
}
```

### 서버 검증

- 경기가 시작된 뒤에만 이동 이벤트를 받는다.
- 각 이벤트 번호가 연속되는지 확인한다.
- 이전 목적지와 다음 출발지가 이어지는지 확인한다.
- 마지막 목적지가 목표 문서인지 확인한다.
- 클라이언트 시간은 참고용으로만 쓰고, 기록은 서버 수신 시각을 기준으로 계산한다.

### 위반 신호

- 링크 클릭 이벤트 없이 문서 URL이 바뀜
- 목표 문서 URL 직접 진입
- 검색 입력 또는 외부 링크 사용 시도
- 경기 탭 밖에서 재개하거나 새 탭으로 문서를 열기

위반 신호는 `경고`로 저장한다. MVP의 최종 실격 여부는 방장이 결과 화면에서 판단한다. 브라우저 확장 프로그램만으로 주소창 조작이나 개발자 도구 조작을 완전히 막을 수 없다는 점을 서비스 안내에 명시한다.

## 7. 시스템 구성

| 영역 | 책임 |
| --- | --- |
| 웹 앱 | 방 생성·입장, 대기실, 경기 현황, 결과 화면 |
| 확장 프로그램 | 나무위키 페이지 감지, 오버레이, 클릭/URL 이벤트 수집, 게임 상태 복원 |
| API/실시간 서버 | 방 상태 동기화, 시작 시각 발행, 이벤트 수신, 검증, 순위 계산 |
| 데이터베이스 | 방, 참가자, 경기, 이동 이벤트, 결과 저장 |

### 권장 초기 기술 선택

- 웹: Next.js + TypeScript
- 확장 프로그램: Manifest V3 + TypeScript (필요 시 React)
- 백엔드/DB/실시간: Supabase (PostgreSQL + Realtime + Edge Functions)
- 배포: Vercel 또는 Cloudflare

## 8. 데이터 모델 초안

| 엔터티 | 주요 필드 |
| --- | --- |
| Room | id, inviteCode, hostPlayerId, status, startArticle, targetArticle, scheduledAt, createdAt |
| Player | id, roomId, nickname, readyAt, connectionStatus, violationStatus |
| Run | id, roomId, playerId, startedAt, finishedAt, durationMs, moveCount, rank, status |
| MoveEvent | id, runId, sequence, fromArticle, toArticle, occurredAt, previousHash, eventHash |
| Violation | id, runId, type, detectedAt, detail, resolvedByHost |

`Room.status`: `waiting` → `countdown` → `running` → `finished`

`Run.status`: `waiting` → `running` → `finished` | `abandoned` | `flagged`

## 9. 개발 일정 제안

### 1주차 — 한 명이 끝까지 달릴 수 있게

- Next.js와 확장 프로그램 기본 프로젝트 구성
- 방 생성/입장 UI와 임시 메모리 상태
- 확장 프로그램 오버레이, 목표 감지, 단일 사용자 타이머
- 이동 로그를 화면에 표시

### 2주차 — 여러 명이 함께 시작하게

- Supabase 데이터 모델과 Realtime 연결
- 대기실 준비 상태, 카운트다운, 서버 기준 시간
- 완주 기록과 실시간 리더보드

### 3주차 — 친선 게임으로 운영 가능하게

- 링크 클릭/URL 변화 기반 이벤트 검증
- 재연결과 새로고침 복구
- 검색·직접 이동 경고, 경로 보기
- 모바일 제외 안내, 오류/빈 상태 UX 정리

### 4주차 — 테스트와 공개 준비

- 실제 방 3~5개로 플레이테스트
- 문서 풀 정리, 문제 문서 제외
- 개인정보·부정행위 한계·나무위키와의 비제휴 고지
- 오류 추적 및 배포

## 10. 성공 기준

- 4명이 같은 방에 입장해 10초 이내로 동시 시작한다.
- 95% 이상의 정상 내부 링크 이동이 경로에 기록된다.
- 목표 도착 후 2초 이내에 임시 순위가 표시된다.
- 새로고침 또는 일시적 네트워크 끊김 뒤에도 경기 상태를 복구한다.
- 첫 플레이테스트에서 참가자 과반이 규칙과 목표를 설명 없이 이해한다.

## 11. 운영 및 법적 고려

- WikiRunner는 나무위키와 제휴하거나 공식 지원을 받는 서비스가 아님을 표시한다.
- 나무위키 서버에 대규모 크롤링이나 자동 요청을 보내지 않는다.
- 게임 진행은 사용자가 일반 브라우저로 직접 열람하는 흐름을 유지한다.
- 문서명·URL은 서비스 운영에 필요한 최소 기간만 저장하며, 방장이 삭제할 수 있는 정책을 둔다.
- 상금·공식 경쟁전 도입 전에는 별도의 공정성·정책 검토가 필요하다.

## 12. 결정이 필요한 항목

1. 첫 버전에서 시작/목표 문서를 방장이 직접 정할지, 운영 문서 풀 랜덤만 제공할지
2. 뒤로가기의 이동 횟수 처리 방식 (권장: 경로에는 기록하고 이동 횟수에서는 제외)
3. 위반 감지 참가자의 자동 실격 여부 (권장: 방장 확인 후 실격)
4. 익명 닉네임만 쓸지, 초기에 Discord 로그인을 함께 넣을지 (권장: 익명으로 시작)
